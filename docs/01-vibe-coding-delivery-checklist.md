# Vibe Coding 软件交付清单

这份清单适合在项目启动、迭代评审和上线前使用。原型、内部工具和生产系统的检查深度可以不同，但风险边界要写清楚。

## 1. 业务理解

- [ ] 写清项目要改善的业务问题，而不是只列功能名称。
- [ ] 明确谁使用系统、谁审批、谁维护数据。
- [ ] 记录现有流程、人工步骤、表格和容易出错的环节。
- [ ] 说明一次错误可能带来的业务、财务或合规影响。
- [ ] 约定上线后观察的指标，例如响应时间、处理时长、错误率或实际使用率。

## 2. 第一版范围

- [ ] 把核心用户任务拆成可以演示和验收的流程。
- [ ] 列出第一版明确不做的功能。
- [ ] 标记涉及权限、资金、隐私、外部接口和数据迁移的高风险部分。
- [ ] 为每项核心能力写出验收条件和示例数据。
- [ ] 确认哪些决定必须由客户或业务负责人批准。

## 3. AI 使用边界

- [ ] 规定哪些资料可以发送给 AI 工具，哪些资料不能离开受控环境。
- [ ] 记录使用的模型、工具、版本和重要提示上下文。
- [ ] 不把模型生成的依赖、配置、权限策略直接视为最终方案。
- [ ] 对 AI 生成的数据库迁移、认证、支付和数据处理代码安排人工审查。
- [ ] 如果 AI 无法解释一段关键代码，先补测试和文档，再决定是否合并。

## 4. 小批量实现

- [ ] 每次提交只解决一个可以验证的问题。
- [ ] 提交信息说明改了什么、为什么改、如何测试。
- [ ] 先让 AI 生成小范围草稿，再由开发者调整接口、错误处理和边界条件。
- [ ] 避免一次生成大量相互依赖的代码后才开始审查。
- [ ] 保留可以回滚的小提交，不用“继续让 AI 修一下”代替定位问题。

## 5. 代码质量与测试

- [ ] 核心业务规则有单元测试或等价的可重复检查。
- [ ] 权限测试覆盖正常用户、越权访问和已失效账号。
- [ ] 对空值、重复提交、超时、限流和第三方错误做异常测试。
- [ ] CI 至少运行格式检查、静态检查、测试和构建。
- [ ] 审查依赖来源、版本、许可证和已知安全问题。

## 6. 上线准备

- [ ] 生产环境变量、密钥和权限由明确负责人管理。
- [ ] HTTPS、域名、备份、日志、监控和告警已验证。
- [ ] 数据库迁移有回滚或恢复方案。
- [ ] 明确发布、暂停、回滚和故障升级流程。
- [ ] 移动端、主流浏览器、表单和关键用户流程完成检查。
- [ ] 客户或业务负责人完成基于真实场景的验收。

## 7. 交接与维护

- [ ] 交付源码、部署说明、环境变量说明和数据结构说明。
- [ ] 说明常见故障、日志位置、备份位置和恢复方法。
- [ ] 关键模块至少有两个人能够理解和修改。
- [ ] 记录第三方服务、模型、账号和续费责任。
- [ ] 约定需求变更、缺陷修复和后续维护的边界。

## 8. 上线后复盘

- [ ] 检查真实用户是否完成核心任务。
- [ ] 对比上线前后的业务指标，不把“上线”本身当成结果。
- [ ] 记录 AI 生成代码带来的返工、调试和维护成本。
- [ ] 把故障和反馈转成下一轮需求，而不是只继续增加功能。
- [ ] 定期检查依赖、模型、权限、备份和恢复流程。
